# CLAUDE.md — xal-projects-dashboard

## Project Overview

A static website to track personal projects — their status, progress, tasks, and blog posts. Built with Astro + React 19.

---

## Technology Stack

- **Framework:** Astro (SSG)
- **UI components:** React 19 (Astro islands, `client:load` for interactive parts)
- **Package manager:** pnpm (never npm or yarn)
- **Testing:** Playwright (end-to-end only)
- **Styling:** CSS (dark theme, rounded corners, responsive)

## Data Schemas

### `data/projects/[project_id].json`

| Field | Type | Notes |
|---|---|---|
| `id` | String | Project identifier |
| `title` | String | |
| `stage` | String | See values below |
| `started_at` | ISO 8601 | Date only (hour/minute irrelevant) |
| `last_activity_at` | ISO 8601 | **Generated** — max of latest task or post `last_activity_at`; falls back to `started_at` |
| `last_task_id` | String | **Generated** — ULID of latest task |
| `last_post_id` | String | **Generated** — ULID of latest post |
| `home_description` | String | HTML string shown on home page card |

**Stage values:** `idea` | `planning` | `in_progress` | `in_production` | `done` | `abandoned`

### Task MDX frontmatter (`src/content/tasks/[project_id]/[task_ulid].mdx`)

| Field | Type | Notes |
|---|---|---|
| `id` | String | ULID of this task |
| `stage` | String | `planned` \| `started` \| `done` |
| `started_at` | ISO 8601 | |
| `last_activity_at` | ISO 8601 | **Generated** — file's last-modified timestamp |

### Blog post MDX frontmatter (`src/content/posts/[project_id]/[post_ulid].mdx`)

| Field | Type | Notes |
|---|---|---|
| `id` | String | ULID of this post |
| `title` | String | Post title |
| `project_id` | String | Parent project ID |
| `published_at` | ISO 8601 | When the post was published |
| `updated_at` | ISO 8601 | Optional — when the post was edited after publishing |
| `tags` | String[] | All lower-case; validated at build time |

`last_activity_at` for a post is derived at build time as `updated_at ?? published_at`. It is not stored in the frontmatter.

### Project description (`src/content/descriptions/[project_id].mdx`)

Body-only MDX; no required frontmatter. Rendered on the project page.

## Generated Fields

Run `pnpm generate` (calls `scripts/generate-fields.mjs`) on plaintext files **before** `pnpm encrypt`. This script:

1. Reads all task `*.md` files (not `*.enc.md`) and updates `last_activity_at` in frontmatter from file mtime.
2. For each project `*.json` (not `*.enc.json`), computes:
   - `last_activity_at` — max of (latest task `last_activity_at`, latest post `updated_at ?? published_at`); falls back to `started_at` if no tasks or posts exist.
   - `last_task_id` — ULID of the lexicographically last task file.
   - `last_post_id` — ULID of the lexicographically last post file.
3. Writes updated values back to each project JSON.

**Workflow:** `pnpm generate && pnpm encrypt && pnpm build` (or `pnpm dev` — both work with encrypted files).
`generate` operates on `data/` (plaintext); `encrypt` reads `data/` and writes `src/content/**/*.enc.md` + `data-encrypted/projects/*.enc.json`; `build` reads those committed files directly.

## Architecture

- **All pages are statically generated** at build time — no server runtime.
- **Interactive islands** (filter, sort, pagination on home and blog list pages) use React 19 with `client:load`. Data is passed as props from Astro at build time.
- **Pagination state is URL-reflected** (`?page=N`) on both the home page and the blog list page.
- **Content collections** (`src/content.config.ts`) use Astro 6's Content Layer glob loaders to enforce schema types for tasks, posts, and descriptions.
- **Tags** on blog posts are validated against a lowercase string constraint at build time via the content collection schema.
- **Content files use `.md` extension** (not `.mdx`) — plain Markdown only; add `@astrojs/mdx` if JSX components in content are needed.
- **Images** are served from `public/photos/`. Missing home-page thumbnails fall back to `public/photos/placeholder_home.jpg`; missing cover images fall back to `public/photos/placeholder_cover.jpg`.

## Pages

### Home (`/`)

- Lists all projects as cards, sorted by `last_activity_at` descending by default.
- Client-side sort toggle: `started_at` or `last_activity_at`.
- Client-side stage filter (multi-select); `abandoned` hidden by default.
- Paginated (10 items per page); current page reflected in URL as `?page=N`.
- Each card: thumbnail (left ~20%), project details (right): title, created date, days since created, last update date, days since last update, stage badge, link button, `home_description`.

### Project page (`/projects/[id]`)

- Cover image at top (`photos/covers/[project_id].jpg`).
- Project title and metadata.
- Active task (stage `started`; at most one per project by design) or "No tasks".
- Latest blog post card (same style as blog list).
- Project description MDX content.

### Blog list (`/blog` or `/blog?page=N`)

- Paginated (10 items per page); current page reflected in URL as `?page=N`.
- Sortable (by `published_at` or `updated_at`).
- Searchable by title (client-side).
- Each post card is widget-like (similar to project cards but no image); displays: title, tags, published/updated date, and the first paragraph of the post body.

### Blog post (`/blog/[projectId]/[postId]`)

Full blog post view.

### Help (`/help`)

Mirrors `HELP.md`. Update `HELP.md` whenever the data format, directory layout, or workflow changes.

## Rules

### Package installation

Any new package must be approved by the user before installation. Never run `pnpm add` or equivalent without explicit user consent.

### Package versions

Always use stable (non-pre-release) versions of packages.

### Supply chain safety

Before installing any package, verify it has not been compromised (check npm advisory database, recent CVEs, maintainer changes). Flag any concerns to the user.

### Task tracking

For every task received, create `.ai_generated/TASK-{EPOCH_MINUTES}.md` first. The file must start with the original request, then list all sub-tasks. Mark each sub-task done as it is completed. Note any unexpected findings or significant deviations.

### Task analysis

Before implementing, document: ambiguities, missing requirements, edge cases, security implications, conflicts with existing architecture. If a critical ambiguity blocks correct implementation, ask the user before proceeding.

### Minimal changes

Think before acting. Keep changes focused and minimal. Do not refactor, clean up, or extend beyond what the task requires.

### Keep CLAUDE.md and HELP.md current

If a task changes the build process, data schema, directory layout, or page design, update this file and `HELP.md` before closing the task.

**Critical:** Any file path shown in `HELP.md` for creating or editing content must point to `data/` (the plaintext editing location, gitignored), never to `src/content/` (the encrypted build artifact, committed). The split is: humans edit in `data/`, the build reads from `src/content/`. If the two ever diverge in HELP.md, fix HELP.md.

### Encrypt/decrypt scripts

Never run `scripts/encrypt.mjs` or `scripts/decrypt.mjs` from the repository root. These scripts read/write committed files (`data-encrypted/`, `src/content/`, `public/photos/`) and would corrupt or expose real data. They may only be run inside `test-env/` against fixture data.

### Files to skip reading

`test-env/README.md` — user-facing documentation only (no code, schemas, or architectural facts). Never read it; all test-infrastructure facts needed for coding are in this file.
